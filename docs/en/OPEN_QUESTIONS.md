## Core Data Model

### Primary student class (`Class`)

- **DECIDED:** a child may belong to only one primary academic class at a time. This is a mandatory business rule of the current version.
- **Target terminology:** `Class` is the child’s permanent primary academic class. Do not mix `Class` with temporary additional groups.
- **Code today:** unique `customer_id` on `course_group_customer` conceptually matches “one primary class”. Table names (`course_groups` vs `Class`) still need terminology normalization.
- **Status:** the rule is DECIDED; schema/API terminology normalization is OPEN.

### Students / parents vs `customers`

- **DECIDED direction:** `customers` is not the long-term Student domain model. Target entities: `students`, `parents`, `student_parent`.
- **Production fact:** there is no valuable user data (test data only). A future migration may be designed without preserving the current test structure at all costs.
- **Do not do now:** migrations, table replacement, or a stable API contract on top of `customers`.
- **Status:** direction DECIDED. Implementation is a separate Core Data Model refactor task.

### Unique vs additional groups

- **DECIDED:** one active `Class` **and**, at the same time, one or more additional groups (events, productions, rehearsals, etc.).
- Additional groups are **not** stored as a second `Class`.
- **Status:** product rule DECIDED. Additional-group schema must not be finalized now.

## Identity & Accounts

**DECIDED for the current version:**

- One User has exactly one primary account type.
- Primary mobile actor types: `student`, `parent`, `teacher`.
- One User **cannot** be Student and Parent, Teacher and Parent, etc. at the same time.

## Teacher Check-in / Staff Presence

**Domain:** proof that a teacher is **physically at the academy**. Distinct from Student Attendance.

**DECIDED semantics:** check-in belongs to the **work day**, **not** to a specific lesson/session. Do not require check-in before every lesson.

**DECIDED workflow:**

1. Teacher opens the Flutter app.
2. Taps **Пришёл** / Check-in.
3. The app takes **one** geolocation snapshot (not background tracking).
4. Backend checks the academy-location geofence.
5. A **daily** teacher check-in is created.

**Conceptual data (not a final schema):** teacher; date; checked_in_at; latitude; longitude; accuracy; academy_location; status; manual correction metadata; audit.

QR is an **optional fallback**, not the primary mechanism.

## Final Assessment / Report Cards

AUB does **not** use a regular school model of continuous grades.

**DECIDED:**

- no running grades during the academic period;
- no electronic gradebook of per-lesson scores;
- only final results are used;
- the report card is produced at the end of the academic period / academic year.

**DECIDED structure (conceptual; not a final schema / no migrations):**

```
AcademicYear → Class → ClassLesson → TeacherAssignment
Student + Class + Lesson + AcademicYear → StudentFinalResult
Student + Class + AcademicYear → ReportCard
```

- The `ClassLesson` set defines report-card disciplines. Do **not** build the discipline list by hand.
- The final result does **not** belong to a teacher. One shared `StudentFinalResult` per subject, even when several teachers are assigned.
- Only teachers assigned to that `ClassLesson` may fill / edit the final result.
- The report card includes **all** class disciplines for the AcademicYear. If any required result is missing, the administrator must get a warning before finalization / PDF generation.
- PDF is **mandatory**. An **Administrator** generates it in the admin panel. Teachers do not generate PDFs. The PDF is **not** a data source of its own.

Preliminary `ReportCard`: student_id; class_id; academic_year_id; status (`draft` / `finalized` / `printed`); finalized_at; generated_at; generated_by. Exact lifecycle may be refined later.

This is a **separate product module**, not part of API Foundation.
